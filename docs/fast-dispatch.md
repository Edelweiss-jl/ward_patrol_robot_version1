# 快速床位分配与路径预排

编辑器使用的 `EditableRuntime` 在任务下发后先给空闲车辆派出可执行床位，再提前计算其余床位的车辆、顺序与路线。无需训练模型，也无需等待前一个床位执行完才开始规划下一个床位。

## 分配与显示

- 首批派车按优先级、截止时间、创建顺序筛选。后续预排在同一优先级、截止时间和释放组内调整空间访问顺序，未来释放的床位排在当前工作之后。
- 比较截止风险、响应是否明显超出目标，再比较楼层覆盖、乘梯次数、调动稳定期和预计完成时间。普通响应超额按支援收益阈值分档，减少为很小的时间收益跨层；高优先级任务直接比较响应和完成时间，可以临时打破驻留要求。
- 同时检查指定车辆、能力、车型通行、累计预计耗电、安全电量及床位互斥；跨楼层预排包含电梯及各层行驶段。
- 任务详情中的“预排 R1 · 队列第 N 床”表示已计算后续安排。床位开始执行时才进入“执行中”。地图中实线为当前行驶路线，按车辆着色的虚线为后续预排路线。
- 车辆完成服务、新任务到达或任务取消/重试后可以提前触发派车，不再固定等待下一个半秒周期。
- 未完成任务的重试不设次数上限，旧任务或模板中的 `retry.max_attempts` 会被忽略。每次实际重试仍递增执行尝试编号，用于隔离旧的采样回执。

快照增加 `dispatch_plan`、`robot_queues` 和 `planning` 字段。每项预排包含车辆、顺序、预计起止、距离、乘梯次数、等梯预算、床位组及各层路径。原 `task_specs.patrol_id` 关联用户创建的主任务。`planning` 提供修订号、数量、累计计算耗时、局部改进次数和改进搜索耗时。

## 楼层驻留与减少乘梯

这套偏好默认启用，同时作用于即时派车和后续预排，覆盖地图中的所有楼层。

1. 各层默认保留一台具备 `patrol` 能力、安全电量且预计能在接单时间窗内恢复服务的车辆。当前身体所在楼层数与预计可接单数分别显示。长任务、低电量、安全驶离过程和人工/MQTT 服务超时不会被直接算成空闲。
2. 持续统计当前、累计和最长服务空窗。未来一段时间内的待执行任务按预计行驶和服务时长计算工作量，为工作量较大的楼层增加目标车辆数；额外车辆仍可灵活接单，不固定锁定车辆身份。
3. 本层能较快接续时优先等待。本层响应明显过长、截止风险增加或高优先级任务到达时允许跨层支援。跨层路线优先减少载车乘梯段数，再比较包含保守等梯预算的耗时。
4. 服务空窗或额外工作量缺口持续超过观察时间后才评估补位，其他用户任务仍在执行时也可以评估。只从仍能保留基本接单能力的楼层选空闲车；已有本层车辆会更早恢复服务时不重复补位。额外工作量支援还须能处理目标任务，且预计收益足以抵消跨层开销。
5. 一次执行一项补位。优先少乘梯，其次选择停车点，再比较耗时和距离；不能使用另一台车预留的停车点，必要时使用窄通道外可达服务点待命。目标须避开其他车辆和近期床位任务的服务位置，缺少安全待命点时保留原因。跨层到达后进入稳定期，普通补位不立即反向调车。普通任务通常保留有用的补位；高优先级、指定车辆或本层无可及时响应的替代车辆时可以中断，已上梯或进入窄通道的车辆先安全驶出。

补位不增加用户床位任务数、巡检完成数或采样次数，使用 `coverage_move_started/completed/cancelled` 独立记录。`floor_coverage` 增加 `ready_counts`、`target_counts`、`workload_seconds`、`vacancy_seconds`、`total_unavailable_seconds`、`max_unavailable_seconds`、`deferred_until` 和基本服务车辆缺口，运行区显示接单能力及空窗。

指定车辆、能力要求和安全电量仍优先遵守。驻留是尽力优化目标，车辆不足、不可达或安全电量不足时保留原因并随条件变化重评。近期有指定任务的车辆不用于普通补位。当前方法不保证全局最少乘梯或全局最优床位组合。

## 电梯等待不确定性

运行时每个乘梯段都计入保守等待预算。观测不足时使用配置区间，默认下沿 30 秒、预算 120 秒；积累至少 8 次实际上梯等待样本后，采用当前仿真小时内的经验 P90，且不低于配置下沿。观测超过 120 秒时不会截断为 120 秒。历史按“电梯、起点楼层、仿真小时（模 24）”分别保留最近 128 条；新运行重新积累。

已知机器人队列、接车和共享占用会提高预算，已上梯车辆只计算剩余乘梯和出梯时间，不再重复计算等梯。故障及出口堵塞仍降低可接单能力。经验分位数和配置区间均是规划估计，实际等待可以更长。

运行页“模拟共享占用”可注入一段无法接入新机器人的时间。它会撤销未上梯的放行，保留排队；已有乘客继续安全运行。样本在真正上梯时记录，撤销放行不会重复产生样本。共享占用由界面/命令注入，历史来自本次仿真的实际排队记录；真实部署需要接入电梯接口并校准参数。

## 空间分组与限时改进

同层床位先按直线距离筛选少量候选，再用真实、有方向的 A* 路程判断分组，避免把隔墙近点误判为相邻。默认半径 6 米、每组最多 4 床、每次至多检查 12 个位置/能力候选。相邻点有连续执行偏好，遇到明显响应或截止风险时仍可换车。周期性重复床位复用坐标索引，已有车辆队列终点的零行驶接续不做无意义跨房间搜索。

得到完整的当前预排后，在独立预算内尝试少量队列头换车和相邻床位换序。每项候选重新计算所有受影响队列的时序、实际路径、累计电量、指定车辆、能力、窄通道目标及床位互斥，只在完整复核且目标改善后一次替换预排。预算耗尽或失败保留原方案，正在执行的床位不参与交换。

## 调整参数

编辑器的“调度偏好”可修改当前运行参数；运行器复核成功后才显示已应用。新运行使用默认值或地图顶层 `dispatch_policy`。代码构造运行器时也可传入 `policy` 字典。所有时间以仿真秒计，暂停不增加服务空窗。

| 参数 | 默认值 | 含义 |
| --- | ---: | --- |
| `response_seconds` / `urgent_response_seconds` | 60 / 20 | 普通/高优先级床位到站响应目标 |
| `emergency_priority` | 1 | 与页面“高”优先级对应 |
| `coverage_ready_seconds` | 30 | 预计可恢复接单的时间窗 |
| `vacancy_grace_seconds` / `rebalance_delay_seconds` | 20 / 15 | 服务空窗阈值/补位需求观察期 |
| `relocation_cooldown_seconds` | 90 | 跨层到达后的普通调动稳定期 |
| `support_gain_seconds` | 20 | 普通响应超额分档和额外支援最低收益 |
| `demand_horizon_seconds` | 120 | 待执行工作量观察范围 |
| `replan_interval_seconds` | 15 | 有待执行床位时周期更新后续预排 |
| `manual_service_seconds` / `mqtt_service_seconds` | 60 / 15 | 人工/MQTT 服务预计时长下限 |
| `elevator_wait_lower_seconds` / `elevator_wait_upper_seconds` | 30 / 120 | 观测不足时的等梯区间 |
| `elevator_wait_quantile` / `elevator_min_samples` | 0.9 / 8 | 经验分位数和最少样本数 |
| `spatial_radius_m` / `spatial_batch_size` / `spatial_candidates` | 6 / 4 / 12 | 分组路程、每组床位数和搜索宽度 |
| `group_switch_seconds` | 5 | 连续相邻床位换车的比较成本 |
| `improvement_trials` / `improvement_budget_ms` | 4 / 12 | 局部交换尝试数与计算目标预算 |

以上为仿真默认启发式参数，需根据任务流与实际等待数据校准。服务超时后继续使用保守的有限剩余时长估计，并降低接单能力；不是把人工确认或 MQTT 服务判为已完成。

命令接口示例（通过既有 `/api/cmd` 提交）：

```json
{"action":"set_dispatch_policy","run_id":"当前运行编号","policy":{"rebalance_delay_seconds":30,"relocation_cooldown_seconds":120}}
```

```json
{"action":"set_elevator_traffic","run_id":"当前运行编号","elevator_id":"E1","busy_for":60}
```

`busy_for: 0` 结束共享占用。策略修改、共享占用和实际排队事件随原命令/事件日志保存，可用于复测。

## 降低重复计算

单层 A* 复用有界的有向栅格边缓存和路线 LRU 缓存，同楼层同车型的车辆共享规划器。线段检查改为连续的圆形车体扫掠与矩形几何相交检测，并用同一规则压缩多余路径点。缓存结果返回独立副本，执行中的路径消耗不会污染后续查询；失败路线也会缓存。

封路更新会替换相应楼层规划器，已观测堵塞按占用格集合复用。新增任务、取消、重试、释放时间、电梯状态、等待样本、共享占用、策略修改和已知堵塞变化触发更新；有待执行床位时另按周期复核。正常运动保留可复用的后续安排。

预排和补位按每片目标 8 ms 在候选路线之间让出控制，局部交换另有计算预算。**单次首次 A*、首批派车、方案复制和快照输出不受这些预算硬限制**。`largest_slice_ms` 用于复测实际最大分片开销。

## 估算边界

这里采用快速启发式预排，不保证全局最优解，也不提供整单原子预约。后续床位的车辆队列属于可修订计划；出发前仍以当前位置、已知封路、电梯状态、电量及床位互斥复核。复核失败会废弃旧预排并重新选择。运行中的测距避障、窄通道和电梯放行继续由各自执行器控制。

预计时刻使用距离/车型速度、配置的服务时长和电梯等待估算。人工确认与 MQTT 实际耗时、转弯加减速、临时避障、多车和窄通道等待可能使实际完成晚于估计；截止风险是提示，不是按时完成保证。电量不足或暂不可达的床位可能没有预排，保持待分配及原有等待原因。暂停期间不推进计算，恢复后继续处理。

## 复测

在项目根目录执行：

```powershell
.\venv\Scripts\python.exe -m unittest tests.test_rolling_dispatch tests.test_floor_coverage tests.test_fast_dispatch tests.test_stage2 tests.test_stage3 tests.test_stage4 tests.test_runtime -q
.\venv\Scripts\python.exe -m tools.benchmark_dispatch --visits 1000
.\venv\Scripts\python.exe -m tools.benchmark_dispatch --visits 200 --layout distinct
```

基准在临时目录运行，不修改已有地图、任务、模型或运行记录。`repeated` 使用内置双病房地图，4 个不同床位反复巡检；`distinct` 使用有一处门洞的分隔地图，生成指定数量的不同服务点。

加入滚动需求、空间分组和限时交换后，本次开发环境的一次测量如下（4 台小型车）：

| 场景 | 首次派车 | 剩余床位预排计算 | 最大预排分片 | 结果 |
| --- | ---: | ---: | ---: | --- |
| 1000 次巡检，4 个不同床位 | 175 ms | 163 ms | 8.3 ms | 4 项执行，996 项预排 |
| 200 个不同床位 | 102 ms | 101 ms | 8.1 ms | 4 项执行，196 项预排 |

以上为派车及预排的计算耗时，不含地图加载、HTTP/SSE、页面刷新及机器人实际行驶时间。基准连续调用分片测量 CPU 工作量，真实运行在仿真帧之间推进，耗时取决于地图、车型、机器负载与缓存命中，不能作为所有场景的延迟承诺。
